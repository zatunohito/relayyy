# 設計セルフレビュー

対象: Cloudflare移行後の [design_overview.md](./design_overview.md)、[infra_design.md](./infra_design.md)、[api-types.ts](./api-types.ts)。

各指摘は「対応済み（文書に反映）」「要判断（利用者の確認が必要）」「許容（MVPとして受け入れる）」のいずれかで整理する。

## 重大度: 高

### R-01 距離の定義が仕様の意図を満たしていない【対応済み・要判断】

- **問題**: 旧設計の区間距離は「同じターンの`start`から`end`」だった。一方で受け取りは「現在のバトン地点から100m以内」でしか成立しないため、各区間は必ず100m以下になる。合計距離はターン数×最大100mの誤差程度の値になり、実際の移動距離（ゲームの主目的）を表さない。
- **対応**: 区間距離を「ターンNの`end`（受け取り地点）から、ターンN+1の`start`（次の設置地点）まで」に変更した（design_overview.md §9、api-types.tsの`totalDistanceMeters`）。データモデルの変更は不要。
- **要判断**: 「バトンを運んだ距離」の定義として、`end_N → start_{N+1}`（実際に歩いた距離）と`start_N → start_{N+1}`（バトン地点間の距離）のどちらにするか。差は最大100m程度。前者を採用した。

### R-02 無料枠超過時にサービスが止まる【許容・運用で対応】

- **問題**: Workers無料プランは1日10万リクエストが上限で、超過するとエラーになる（課金はされない）。60秒ポーリングでは、常時起動している端末が約70台で上限に達する。
- **対応**: アプリがフォアグラウンドの間のみポーリングする前提を明記し、1日約3,000人まで賄える見積もりを示した（infra_design.md §10）。ユーザー増加時は月額$5の有料プランへ移行する。

## 重大度: 中

### R-03 ターン取得の読み取りが履歴の長さに比例して増える【対応済み】

- **問題**: 無限リレーで`turns`が増え続けるため、毎回全件取得するとD1の読み取り行数・レスポンスサイズ・通信量が増え続ける。
- **対応**: `GET /teams/{teamId}/turns?since=`による差分取得を追加した。ポーリング1回の読み取りは常に数行になる。クライアントは確定済みのターンをローカルに保持する。

### R-04 メンバー追加の読み取り→書き込み競合【対応済み】

- **問題**: `members`をJSON配列として持つため、アプリ側で読み出して追記すると、同時参加で片方の追記が失われる。
- **対応**: SQL内で`json_insert`により追記する。あわせて人数上限（50人）を同じ文で判定する。

### R-05 採番とバトン設置の前提確認が別々だと競合する【対応済み】

- **問題**: 「最新ターンを取得→+1で挿入」を別々に行うと、受け取り前に設置される、または番号が衝突する。
- **対応**: 1文の`INSERT ... SELECT ... WHERE NOT EXISTS(未受け取りのターン)`に統合した。衝突時は主キー違反を`409 CONFLICT`にマップする。

### R-06 タグのドメイン検証がサーバーでできない【許容・仕様に明記】

- **問題**: 設計上、サーバーには緯度・経度しか届かないため、NFC/QRのURLドメイン検証はアプリ側でしか行えない。改造したクライアントは検証を迂回できる。
- **対応**: 偽造対策を行わないというMVP方針と整合するため許容し、design_overview.md §3に「アプリ側で検証する」と明記した。

### R-07 NFCのURLに使うドメインが未確定【要判断】

- **問題**: タグに焼き込んだURLは後から変更できない。ドメイン未確定のままタグを配布すると作り直しになる。
- **対応**: インフラ設計書 §9で「タグの配布前に独自ドメインを確定する」ことを明記した。MVPのアプリ内読み取りは`*.workers.dev`のままで動く。ドメインの決定は利用者の判断が必要。

## 重大度: 低

### R-08 D1の書き込みリージョンが遠いとレイテンシが増える【対応済み】

D1のプライマリは作成時に決まり、後から変更できない。作成時に`--location=apac`を指定する手順を追加した（infra_design.md §5）。

### R-09 認証なしのため`teamId`と参加コードが実質的なパスワード【許容】

`teamId`はUUIDv4（推測困難）、参加コードは約8.9億通り。総当たりはMVPでは許容し、公開後はRate Limitingで対処する（infra_design.md §7）。

### R-10 メンバーが全員同名でも区別できない【許容】

仕様どおり（design_overview.md §6）。`receive`の実行者と設置者が同一かどうかは検証しない。バトンを受け取った人が離脱した場合でも、他のメンバーが次のバトンを置ける。

### R-11 二重送信（リトライなし）で重複チームが作られうる【許容】

`POST /teams`に冪等性キーがない。電波が不安定な状況で二重にタップすると、空のチームが増える。不要チームの掃除は将来課題（infra_design.md §5）。

### R-12 バックエンドとフロントでHaversineが二重実装になる【許容】

共有パッケージ化（bunワークスペース）はExpo/Metroの設定が複雑になるため、MVPでは小さな関数を両側に置く。型定義は`docs/api-types.ts`を正とし、Zodスキーマと手動で一致させる。ずれが出た時点で共有化を検討する。

### R-13 無料枠・上限値の一部が未確認【要確認】

公式ドキュメントへ接続できず、無料枠、Time Travelの保持期間、`wrangler`の設定キー名は確認できていない（infra_design.md冒頭に注記）。実装着手前に公式ドキュメントと照合すること。
